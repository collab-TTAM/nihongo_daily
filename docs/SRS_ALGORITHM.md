# SRS interval policy — nd-srs-1

Issue #4 supplies an immutable, deterministic **pure Dart core** for Personal
Alpha. The app still shows its preview page. The private SQL port and local
authenticated transaction increment in #22 are
documented in SRS_RPC.md. No hosted review endpoint, real Auth, offline queue or
real study integration is claimed; #22/#15 and the study flows retain those gates.

This is a conservative explicit interval heuristic, not an FSRS implementation,
SM-2 compatibility claim or calibrated prediction of human memory. It requires no
trained parameters, provider or package dependency. Learning outcomes must be
observed later; changing these rules requires a new algorithm version and parity
cases rather than silently altering a server port.

## Inputs and state

`SrsCard` projects item_type/id, scheduling state, interval_days, difficulty,
review/correct/incorrect counts and last/next review instants. `SrsReview` encodes
exactly the seven frozen submit_review fields; it never accepts user_id or derived
state. Difficulty is finite [0,1]. Counters are nonnegative PostgreSQL integers,
and correct + incorrect equals total. NEW has zero history, interval and null
review dates. Reviewed states require positive interval and ordered dates.

All instants are converted to UTC. Scheduling uses the event instant explicitly,
never DateTime.now(), local midnight, random jitter, response time or a timezone
calendar date. Durations use fixed 86,400-second days and integer microseconds.
Typed DateTime/request encoding does not replace raw JSON schema/auth validation.
The future decoder must preserve valid wire precision and immutable retry input;
this core does not implement a raw JSON parser or canonicalize arbitrary input.

The rating mapping remains AGAIN/HARD/GOOD/EASY = 0/1/2/3. Only AGAIN is incorrect.
Reject mismatched content identity, malformed typed values and counter overflow.
A new event earlier than last_review_at throws StaleSrsReview (SYNC_CONFLICT).
Equal instants are allowed for distinct events. MASTERED is reserved and rejected
as a v1 scheduling input; the core never emits it. Progress mastery is separate.

## Transition table

Times are measured forward from the supplied review instant.

| Previous state | AGAIN | HARD | GOOD | EASY |
| --- | --- | --- | --- | --- |
| NEW | LEARNING, 1 minute | LEARNING, 5 minutes | LEARNING, 10 minutes | REVIEW, 4 days |
| LEARNING | LEARNING, 1 minute | LEARNING, 5 minutes | REVIEW, 1 day | REVIEW, 4 days |
| RELEARNING | RELEARNING, 1 minute | RELEARNING, 5 minutes | REVIEW, 1 day | REVIEW, 4 days |
| REVIEW | RELEARNING, 1 minute | REVIEW, formula below | REVIEW, formula below | REVIEW, formula below |

There is no hidden learning-step column. A successful GOOD after the initial
learning step graduates to a one-day review. Failure during review enters
relearning. Repeated failures retain short retry intervals; a successful
relearning review starts conservatively instead of immediately restoring a long
previous interval.

For every accepted review, adjust difficulty by +0.15/+0.05/-0.02/-0.05 for
AGAIN/HARD/GOOD/EASY. Clamp to [0,1], then round to six decimal places. Let d be
this new difficulty. Round positive durations once to the nearest microsecond,
then store interval_days as that integer duration divided by 86,400,000,000.

For a REVIEW success:

- elapsed = (event - last_review_at) in days.
- base = min(365, previous interval_days, max(1, elapsed)). Early repeated reviews
  receive elapsed-time credit, preventing repeated taps from compounding a long
  future interval.
- overdue = max(0, (event - next_review_at) in days).
- HARD: max(1, base × 1.2), with no overdue bonus.
- GOOD: max(1, (base + min(overdue / 2, base)) × (2.5 - d)).
- EASY: max(4, (base + min(overdue, base)) × (3.0 - d)).
- Cap the result at 365 days. Due/overdue intervals obey HARD ≤ GOOD ≤ EASY;
  very late reviews have bounded credit.

Increment review_count once; increment exactly one correctness counter. Return a
new card and leave the input unchanged. The five-field public response encoder
matches contracts/v0.1. Stability/retrievability are **not** estimated by this
policy; a backend adapter must preserve those reserved values instead of
fabricating a memory model. Algorithm version is internal metadata, not an extra
field in the frozen response.

## Shared evidence and backend handoff

`contracts/srs/v1/golden.json` contains 26 hand-selected transition/interval
examples: all first ratings, learning/relearning, due/early/overdue success, caps,
difficulty rounding, Vietnam midnight, DST transitions and microsecond instants.
Expected durations are policy examples, not generated by the Dart scheduler.

Flutter unit tests consume these cases and exercise malformed state/request
boundaries, immutable/deterministic output, item identity, equal/stale instants,
all content types, rating order, bounded repeated early reviews and long
histories. The standalone tool also emits the **actual** Dart request/response
JSON; Python validates it against frozen schemas and the expected parity cases.
CI runs both, then the retained web/Windows builds and SQL security suite.

```bash
cd apps/flutter_app
flutter pub get --enforce-lockfile
dart format --output=none --set-exit-if-changed .
flutter analyze
flutter test
mkdir -p build
dart run tool/verify_srs.dart build/srs-wire-output.json
cd ../..
python3 -m pip install -r contracts/requirements.txt
python3 -m contracts.validate_srs_wire apps/flutter_app/build/srs-wire-output.json
```

#22 must port nd-srs-1 with these parity cases, verified identity, active-content
checks, row locking and an atomic event/state transaction. Record the algorithm
version in backend event metadata. Check stored duplicate receipts before stale
rejection, replay the original result, conflict on changed retry input and enforce

Never accept a client's projected card, counters or next_review_at as authority.
Changing difficulty/interval policy later does not rewrite historical receipts.
